Operational verdictHIGH-RISK

Executive verdict. This is a single-operator setup: Claude Code (desktop app) with the Superpowers plugin, working on a static Cloudflare Workers site. It reliably does interactive, human-supervised site edits. The historical transcripts show the agent previewing and screenshotting changes before pushing. But it has no test or eval suite, no CI gate, no independent review, and no durable task state. A broad permission allowlist lets the agent push straight to main, which the README says deploys to production. A live Cloudflare API token is stored in plaintext in the local permission allowlist and in two session transcripts. The low raw score mostly reflects capabilities that don't exist here, not broken ones. The HIGH-RISK verdict comes from the secret exposure and the ungated path to production.

Scope, revision, environment, limitations

  • Repo: /Users/naeem/naeem-website, branch main, HEAD 878723c (2026-09-23), working tree clean at start, 96 commits, remote github.com/naeemsmood/naeem-website.
  • Runtime: macOS (Darwin 25.5.0), Claude Code desktop app (this session runs Opus 5.5), Node v24.12.0, Python 3.13.7, gh authenticated (keyring). claude CLI and wrangler are not on PATH. Wrangler runs only through npx, which downloads it on demand.
  • Plugins installed: superpowers 5.1.0, frontend-design 1.0.0 (user scope).
  • Limitations: No Cloudflare dashboard or API access was used, so Workers Builds, production secrets and D1 were not inspected. I didn't install wrangler, so there was no wrangler dev run. Live-site checks were unauthenticated GET status codes only. No synthetic facts were written to production memory.
  • Parallelism: Audit lanes were not run as parallel sub-agents. Given the repo's size, the lanes ran inline in the lead session, using concurrent independent tool calls.

Findings (severity-ranked)

HIGH · Config / secret exposure (J) · confidence: high

Plaintext Cloudflare API token stored locally. .claude/settings.local.json:34 embeds a CLOUDFLARE_API_TOKEN=cfut_… value inside a permission rule. The same value appears in 2 session transcripts under ~/.claude/projects/…/*.jsonl. The file is gitignored, and git log -S cfut_ across all refs finds 0 hits, so it isn't in git history.

Failure scenario: Any process, backup, or shared transcript that reads these files gets a deploy-capable token for the production Worker.

Fix: Rotate the token in Cloudflare, delete the rule from the allowlist, and use wrangler login or a keychain-backed env var. Verify: grep -rl cfut_ ~/.claude .claude returns nothing, and the old token is revoked in the dashboard.

HIGH · Delivery lifecycle / uncontrolled execution (A, J) · confidence: high

Ungated agent path to production. The allowlist pre-approves git push * (line 33), git reset * (41), npx wrangler * (48) and env (216), among 221 Bash rules. The README says pushing to main deploys. There's no CI, test, or review gate (.github/ is absent).

Failure scenario: An agent pushes a broken or destructive change, or runs wrangler d1 execute against production, with no prompt and no check.

Fix: Prune the allowlist to read-only commands and keep push/deploy/reset/env on ask. Deploy from a preview branch, or add a minimal CI link-check before production. Verify: In a fresh session, git push triggers a permission prompt.

MEDIUM · Delivery correctness (A) · confidence: high on the code path, the production state is UNVERIFIED

Admin auth fails open if its secrets are missing. src/worker.js:51 builds the expected header from env.ADMIN_USER/ADMIN_PASSWORD. When they're unset, the credential undefined:undefined is accepted. I reproduced this in an isolated Node test with mocked bindings: 200 with the secrets unset, 401 with them set. Production returned 401 to an unauthenticated GET. I did not probe production with that credential.

Fix: Return 503 when either secret is missing, and compare in constant time. Verify: Rerun the scratch test and confirm 503 or 401 in the unset case.

MEDIUM · Exposure (J) · confidence: high

"Private" pages are publicly reachable, and robots.txt lists them. /research-private and /peak-life-os-private return 200 live. Protection is only noindex plus robots.txt Disallow lines, and those lines publish the URLs.

Fix: If the content is non-public, gate these paths in the Worker (reuse requireAuth) and drop them from robots.txt. Verify: An unauthenticated GET returns 401.

MEDIUM · Evaluation & telemetry (D, E) · confidence: high

No independent outcome record. Completion evidence exists only inside session transcripts, as the authoring agent's own screenshots and curl checks. There's no ledger of attempted, failed, or abandoned work.

Fix: Add a small checks/ script: an internal link and asset checker over public/, plus a Node test of worker.js like the one used here. Run it before push, and append results to a local log. Verify: The script exits non-zero on a deliberately broken link.

LOW · Config consistency / context (G, J) · confidence: high

Stale README and no project instructions file. README.md:8-16 gives port 8843 and /public/, and lists the retired work-with-me.html. It doesn't mention the Worker, D1, or /admin. launch.json serves the repo root on 8845, so root-relative links and clean URLs don't resolve as they do in production. There's no CLAUDE.md capturing the deploy rules.

Fix: Refresh the README, add a short CLAUDE.md (deploy = push to main, what needs a preview check, private-page policy), and point the preview at public/. Verify: Links click through correctly in the local preview.

LOW · Learning (I) · confidence: medium

Memory is unversioned and unevaluated. It's a single entry outside git, with no review or rollback path. That's adequate at this scale, but a bad memory can't be audited or reverted.

Fix: Periodically review memory (for example with the consolidate-memory skill) and keep project-policy rules in a versioned CLAUDE.md instead.

Remediation plan (ordered)

  1. Rotate the Cloudflare token, then remove it from settings.local.json and scrub it from the transcripts.
  2. Prune the permission allowlist, and put push, deploy, reset, and env back on ask.
  3. Make requireAuth fail closed, then confirm production secrets exist with wrangler secret list (run by you).
  4. Decide the policy for the private pages: gate them, or accept that they're public.
  5. Add a pre-push check script (links plus a Worker unit test) and a CLAUDE.md that requires running it.
  6. Refresh the README and the launch.json preview root.

Verified operating scope

The evidence supports attended work only. The user requests a change in chat, the agent edits static HTML/CSS or the Worker, previews it locally, and pushes, with the user watching. Nothing reproduced in this audit shows that work is verified independently of the authoring agent, recovers from interruption, or would be safe unattended. The current allowlist would let an unattended session deploy to production with no gate. Evidence stops at: the Worker's routing and auth logic (unit-level, mocked), live HTTP status codes, and historical transcripts showing self-verification.
